1. 1 - O que são operações de “Commit”, “Push” e “Pop” efetuadas num repositório?

    • O comando "commit" regista no histórico do repositório local as alterações que selecionámos, acompanhado de um comentário descritivo da ação tomada, exemplo "commit file 'Perguntas.txt'. Funciona como um ponto de referência ao qual podemos voltar. Fazer "commit" não envia automaticamente as alterações para o GitHub. (Git, s.d., git-commit)

    • O comando "push" envia os commits locais para um repositório remoto, como o GitHub, permitindo partilhar as alterações. (Git, s.d., git-push)

    • O comando "pop", através de "git stash pop", recupera alterações que tinham sido guardadas temporariamente com "git stash" e aplica-as ao trabalho atual. Se a aplicação decorrer sem conflitos, essa entrada é retirada da lista de alterações guardadas. (Git, s.d., git-stash)

  2. 2 – Quais sáo as vantagens de usar Branchs num repositório git?

    As "branchs" são ramificações que permitem desenvolver novas funcionalidades, corrigir erros ou experimentar ideias sem alterar diretamente a versão principal do projeto. Facilitam também o trabalho em equipa, porque cada pessoa pode trabalhar numa "branch" e integrar depois as alterações através do comando "merge". Isto ajuda a separar tarefas e a testar o trabalho antes de o juntar à versão principal. (Chacon & Straub, 2014)

  3. 3 – Nos Merges de conteúdos resultantes de um “Pop” podem resultar em conflitos. Em que consistem e como podem ser resolvidos esses conflitos?

    Um conflito pode surgir quando o Git não consegue combinar automaticamente as alterações nos ficheiros. Por exemplo, ao recuperar as alterações com "git stash pop", podemos ter versões diferentes da mesma linha e o Git não sabe qual deve manter.

    Para resolver o conflito, analisámos os ficheiros afetados, escolhemos o conteúdo correto ou combinamos as duas versões, finalmente removemos os marcadores de conflito. Após a resolução do conflito, guardámos os ficheiros, verificámos o resultado e usamos "git add" para marcar a resolução. Finalmente executamos um "commit" para registar as alterações.

    Se o conflito resultar da execução de "git stash pop", a entrada mantém-se guardada no "stash", e só deve ser removida depois de confirmar que recuperámos tudo corretamente. (Chacon & Straub, 2014; Git, s.d., git-stash)

  4. 4 – “Clone” e “Fork” são formas diferentes de replicar um repositório Git. Quais as diferenças entre eles?

    O "clone" cria uma cópia local de um repositório, normalmente no nosso computador, incluindo o histórico. Permite trabalhar nos ficheiros localmente, mas não nos dá, por si só, autorização para enviar alterações para o repositório original. (Git, s.d., git-clone)

    O "fork", no GitHub, cria um repositório separado na nossa conta, a partir de outro, mantendo uma ligação ao original. Podemos alterá-lo e propor que essas alterações sejam integradas no projeto original através do comando "pull request", ou seja, um pedido de integração. É habitual criar primeiro um "fork" e depois cloná-lo para trabalhar no computador. (GitHub, s.d.)
